Resources: context with a URI 7 min live

A resource is read-only content the application decides to attach to a conversation. You register one with @mcp.resource("uri"): the decorator argument is the URI, the function returns the content, and the return type hint sets the mime type. The URI scheme is yours to design - daybreak:// here - and it is how the app addresses the content.

LiveThe catalog resource, line by line4 min▶

Daybreak's catalog is computed from the database every time it is read - not a static file. That is the point of a resource function: it can run code. Here it queries products and formats a markdown list.

python · a computed resource@mcp.resource("daybreak://catalog") def catalog() -> str: """Daybreak product catalog with prices.""" rows = _query("SELECT name, category, price, roast FROM products ORDER BY price DESC") lines = ["# Daybreak catalog"] for name, category, price, roast in rows: roast_note = f" ({roast})" if roast else "" lines.append(f"- {name} - {category} - ${price:.2f}{roast_note}") return "\n".join(lines)
  • @mcp.resource("daybreak://catalog") - the URI is the argument; the function name catalog becomes the resource name.
  • Returns str, so the mime type is text. Return bytes or set a type for binary content.
  • Computed live - add a product to the db and the next read reflects it. No caching to invalidate.
LiveURI design taste - nouns, hierarchies, no verbs3 min▶

The scheme is yours, so design it like an API surface, not a dumping ground. Daybreak uses daybreak://catalog and daybreak://policy/refunds - notice the second one nests under a policy/ namespace.

  • Nouns, not verbs. Resources are things you read. daybreak://catalog, not daybreak://get-catalog. Verbs are for tools.
  • Hierarchies group. policy/refunds, policy/shipping - a namespace that scales as you add docs.
  • Stable + addressable. The app stores the URI; renaming it breaks references. Choose once.
  • Your scheme, your rules. daybreak:// means nothing to anyone else - and that is fine. It only has to be consistent within your server.
Static vs computed A resource can return a constant (like the refund policy text) or run a query (like the catalog). Both are just functions - the caller cannot tell which, and should not have to.

Prompts: playbooks users pick 7 min live

A prompt is a server-authored template the user chooses on purpose - it shows up as a slash command or menu item in the host. Register it with @mcp.prompt(); the function's parameters become the form fields the host renders. Daybreak ships one: monthly_report(month), the founder's standing ops report.

Livemonthly_report, walked through4 min▶

The prompt returns the text that will be handed to the model when the user picks it. Its month parameter becomes a field the host asks the user to fill - which is why the wire message carries an arguments declaration.

python · the prompt@mcp.prompt() def monthly_report(month: str) -> str: """Standard monthly ops report for the founder.""" return ( f"Write the {month} ops report for Daybreak: orders and revenue vs the " f"previous month, refunds, subscription changes, and one concrete " f"action for next month. Use query_sales, top_products and " f"subscription_status for the numbers - do not estimate." )
  • month: str becomes a required argument the host renders as a field - the same wire mechanism as a tool's input schema.
  • The template tells the model to use the tools - a prompt orchestrates your own primitives. Pick monthly_report for 2026-03 and the model will call query_sales, see $150.00, and write the dip up.
  • "do not estimate" - the prompt is where you encode the house rules for a recurring task.
Self-studyWhen a prompt beats a system-prompt doc3 min read▶

You could paste "here is how we write the monthly report" into a system prompt and be done. Sometimes that is right. But a prompt primitive wins when:

  • The user should trigger it explicitly. A slash command is discoverable and intentional - the user knows they are running the report, versus hoping the model remembers a buried instruction.
  • It takes arguments. month is a parameter, not a copy-paste edit. The host collects it cleanly.
  • It lives with the server. Update the report format once, on the server, and every host that connects gets the new version - no chasing pasted system prompts across teammates.

Rule of thumb: reusable, parameterized, user-triggered workflows are prompts. One-off context is a system prompt. Recurring reference material is a resource.

Round out the server 5 min live

The server trio is complete. Two utilities exist that you should know by name even though Daybreak does not need them yet, and then we confirm your file matches the reference exactly.

Self-studyCompletion and pagination, briefly and honestly2 min read▶

Two protocol utilities you will meet in bigger servers, named here so they are not a surprise:

  • Completion - the server can offer autocomplete suggestions for a prompt or resource argument (like a month picker suggesting valid months). Nice UX, optional, skipped here.
  • Pagination - when a list response is long, the server returns a cursor and the client asks for the next page. Daybreak lists three tools and two resources, so there is nothing to paginate. You will care about this when a server exposes hundreds of resources.

Neither changes how you write tools, resources, or prompts - they are protocol plumbing the SDK handles when you need them.

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · In @mcp.resource("daybreak://catalog"), who defines the daybreak:// scheme?

The scheme is yours. daybreak:// means nothing outside your server, and that is fine - it just has to be a stable, addressable name the app can store and read from.

2 · What do a prompt function's parameters become?

A prompt's parameters (like monthly_report's month) travel as an arguments declaration on the wire, which is exactly what lets the host render a form and collect the user's input.

3 · Who controls when a resource enters the conversation?

The control triangle: model controls tools, user controls prompts, app controls resources. The application decides which read-only content to attach; the server only offers it.
