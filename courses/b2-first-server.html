FastMCP and your first tool 7 min live

A FastMCP server is a Python object you decorate functions onto. Instantiate it with a name, decorate a function with @mcp.tool(), and the SDK reads the function's name, its docstring, and its type hints to build the tool's name, description, and inputSchema - the exact three fields you saw in tools/list last session. You write Python; the wire format is derived.

python · server.py, top of fileimport pathlib import sqlite3 from mcp.server.fastmcp import FastMCP DB_PATH = pathlib.Path(__file__).parent / "daybreak.db" mcp = FastMCP("daybreak-mcp") def _query(sql: str, params: tuple = ()) -> list[tuple]: con = sqlite3.connect(DB_PATH) try: return con.execute(sql, params).fetchall() finally: con.close()
Livequery_sales, line by line4 min▶

Here is the real tool from the running project - not a toy. Read it top to bottom: the decorator registers it, the signature declares the interface, the docstring documents it for the model, and the body just queries SQLite and returns a string. Every MCP tool result in this course is a string.

python · the first real tool@mcp.tool() def query_sales(month: str) -> str: """Order count, refunds, and completed revenue for one month (YYYY-MM).""" rows = _query( """ SELECT o.status, COUNT(DISTINCT o.order_id), COALESCE(SUM(oi.quantity * oi.unit_price), 0) FROM orders o JOIN order_items oi ON oi.order_id = o.order_id WHERE substr(o.order_date, 1, 7) = ? GROUP BY o.status """, (month,), ) if not rows: return f"No orders found for {month}." by_status = {status: (n, rev) for status, n, rev in rows} total = sum(n for n, _ in by_status.values()) completed_rev = by_status.get("completed", (0, 0.0))[1] refunded = by_status.get("refunded", (0, 0.0))[0] return ( f"{month}: {total} orders ({refunded} refunded), " f"completed revenue ${completed_rev:.2f}." )
  • month: str - one required string argument. The model must supply it; the Inspector will show a required field.
  • The docstring spells out the format (YYYY-MM). That single parenthetical stops the model guessing "March" instead of "2026-03".
  • Refunds are excluded from revenue by grouping on status - the March refund is why completed revenue is $150.00, not more.
LiveWriting tool descriptions the model uses well4 min▶

This is the craft point of the whole session. The docstring is not documentation garnish - it is the interface the model reads before every call. Watch the discovery message again and notice the description is the only prose the model gets:

Four rules that make descriptions the model acts on correctly:

  • State the format in the description, not just the type. (YYYY-MM) beats "a month string" every time.
  • Say what it returns and what it excludes. "completed revenue" tells the model refunds are already handled - it will not double-correct.
  • One tool, one job. A tool that both queries and mutates confuses the model about when it is safe to call.
  • Name the function like the action. query_sales reads as a verb; the function name becomes the tool name.
Real world

The tool nobody could call. A team shipped a get_data tool with the docstring "Returns data." The model never picked it correctly because it could not tell what data or when. Renaming it query_sales and writing one sentence about the month format and the revenue definition fixed the call rate overnight - no model change, just the description.

Run it and poke it: the Inspector 6 min live

One command runs your server and opens a browser devtool wired to it - the MCP Inspector. It is the single most useful thing in your toolkit this track: it lists your tools, lets you call them with arguments, and shows the raw result, so you never guess whether a bug is in your code or on the wire.

bash · launch the Inspectoruv run mcp dev server.py # opens the Inspector in your browser, connected over stdio # tabs: Tools · Resources · Prompts · and a live message log

Run uv run mcp dev server.py. The Inspector opens and connects; if it does not, the server threw on import - read the terminal.

Open the Tools tab. You should see query_sales with its description and a month field. That is your docstring and type hint, rendered.

Type 2026-03 into month and press call. Read the result string: it should say completed revenue $150.00.

Call it again with 2026-02 - $271.00. You just proved the March dip through your own server.

LiveInspector traffic vs the wire scenarios3 min▶

The stepper above is the same JSON-RPC the Inspector generates when you click "call". The Inspector is just a host that never involves a model - you play the model, choosing the tool and filling the arguments by hand. That is exactly why it is the right debugging tool: it removes the model's judgement so you can test the server in isolation.

  • Tools tab = the tools/list response, rendered as a form.
  • Calling a tool = one tools/call request and its result - the log tab shows the raw JSON.
  • A red result with isError:true = your tool ran and raised; a protocol error = the Inspector could not even reach the tool.
Self-studyCommon first-server failures3 min read▶

Three failures catch nearly everyone once. Recognize them and you save the afternoon:

  • Path. The server cannot find daybreak.db because it was launched from a different directory. Fix: DB_PATH is built from __file__ in the project, so keep server.py and the db together.
  • Unseeded db. Tools return "No orders found." Fix: run python seed_daybreak.py.
  • Silent exceptions. A tool raises but you only see a generic error in the host. Fix: run in the Inspector, which surfaces the traceback - and never print to stdout in a stdio server, because stdout is the protocol channel. Use stderr or logging.
stdio means stdout is sacred A stdio server sends every protocol message over stdout. A stray print("debug") corrupts the JSON stream and the host disconnects. Log to stderr instead.

Add two more tools ★ 10 min · build

Two tools give the server real range: top_products takes a date range with defaults, and subscription_status takes no arguments at all. Notice how the signatures change what the Inspector renders.

python · finished code, paste and re-run the Inspector@mcp.tool() def top_products(from_date: str = "2026-01-01", to_date: str = "2026-12-31") -> str: """Best-selling products by quantity for a date range (YYYY-MM-DD).""" rows = _query( """ SELECT p.name, SUM(oi.quantity) AS qty FROM order_items oi JOIN orders o ON o.order_id = oi.order_id JOIN products p ON p.product_id = oi.product_id WHERE o.order_date BETWEEN ? AND ? AND o.status = 'completed' GROUP BY p.name ORDER BY qty DESC LIMIT 5 """, (from_date, to_date), ) if not rows: return "No completed sales in that range." lines = [f"{i + 1}. {name} - {qty} sold" for i, (name, qty) in enumerate(rows)] return "Top products " + from_date + " to " + to_date + ":\n" + "\n".join(lines) @mcp.tool() def subscription_status() -> str: """Active vs cancelled subscription counts, with monthly quantities.""" rows = _query( """ SELECT CASE WHEN cancel_date IS NULL THEN 'active' ELSE 'cancelled' END, COUNT(*), SUM(monthly_qty) FROM subscriptions GROUP BY 1 """ ) parts = [f"{status}: {n} subs ({qty} bags/month)" for status, n, qty in rows] return "Subscriptions - " + "; ".join(parts)

Paste both under query_sales, save, and restart the Inspector.

top_products shows two fields, both pre-filled with defaults - that is what the = "..." defaults do to the schema (optional, with a default).

subscription_status shows no fields and a call button - a zero-argument tool. Call it and read active vs cancelled.

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · With FastMCP, what does a tool function's docstring become?

FastMCP derives the tools/list entry from your function: name from the function name, description from the docstring, inputSchema from the type hints. The docstring is the interface, not a comment.

2 · Your stdio server disconnects the moment a tool runs. Likeliest cause?

In stdio transport, every protocol message travels over stdout. A stray print() corrupts the JSON stream and the host drops the connection. Log to stderr instead.

3 · What is the MCP Inspector for?

The Inspector is a host that lets you play the model: pick a tool, fill arguments, see the raw result. It isolates the server so you can tell a code bug from a protocol problem.
