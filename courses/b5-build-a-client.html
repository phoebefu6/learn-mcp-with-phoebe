The other side of the wire 7 min live

The server is passive: it waits and answers. The client is active and owns four jobs. It owns the connection (it launches or dials the server), the session (it sends initialize and holds the agreed capabilities), discovery (it calls tools/list and hands the schemas to the model), and routing (when the model asks for a tool, the client is who actually sends tools/call). Every message you watched in b1 was sent or received by a client - tonight that client is your code.

LiveClientSession and stdio_client, line by line4 min▶

The Python SDK gives you two pieces. stdio_client launches the server as a subprocess and hands back a read/write pair of streams. ClientSession wraps those streams in the JSON-RPC machinery - initialize, list_tools, call_tool, and the rest. You open both as async context managers so they close cleanly.

connect.py · the minimum viable client import asyncio from mcp import ClientSession, StdioServerParameters from mcp.client.stdio import stdio_client # Tell the SDK how to LAUNCH the server (this is the stdio transport). params = StdioServerParameters(command="python", args=["server.py"], env=None) async def main(): async with stdio_client(params) as (read, write): async with ClientSession(read, write) as session: await session.initialize() # the handshake from b1 tools = (await session.list_tools()).tools # runtime discovery print("Tools:", [t.name for t in tools]) result = await session.call_tool("query_sales", {"month": "2026-03"}) print(result.content[0].text) asyncio.run(main())

That is a complete client. Run it and you get the same tools/list and tools/call traffic you stepped through in b1 - but sent by you. Below, watch the call your last line makes go over the wire.

LiveSession lifecycle - open once, reuse, close cleanly3 min▶

A session is not per-request; it is per-connection. You initialize once, then send many calls over the same live session. The official quickstart uses an AsyncExitStack so the connection and session are torn down in the right order even if something throws.

DaybreakClient · a reusable session holder from contextlib import AsyncExitStack from typing import Optional from mcp import ClientSession, StdioServerParameters from mcp.client.stdio import stdio_client from anthropic import Anthropic from dotenv import load_dotenv load_dotenv() # reads ANTHROPIC_API_KEY from .env class DaybreakClient: def __init__(self): self.session: Optional[ClientSession] = None self.exit_stack = AsyncExitStack() self.anthropic = Anthropic() async def connect(self, server_script: str): params = StdioServerParameters(command="python", args=[server_script], env=None) read, write = await self.exit_stack.enter_async_context(stdio_client(params)) self.session = await self.exit_stack.enter_async_context(ClientSession(read, write)) await self.session.initialize() tools = (await self.session.list_tools()).tools print("Connected. Tools:", [t.name for t in tools]) async def cleanup(self): await self.exit_stack.aclose()
  • Who starts the handshake? The client - always. session.initialize() sends the first message; the server only answers.
  • Where do capabilities live? Agreed once, in the initialize exchange. On the current spec (2025-11-25) the session carries them until you close it.
  • Changes 2026-07-28: the stateless core removes this explicit handshake - capabilities travel in _meta on each request. b8 walks that delta.

The chatbot loop 7 min live

A client that only calls tools you hardcode is not interesting. The chatbot loop makes the model decide. The shape is always the same: user message → send it to the model with the tool definitions → the model returns tool_use blocks → for each, call session.call_tool → feed the tool_result back → the model writes the final answer. This loop is identical whether the model is Claude in the cloud or Llama on your laptop; only the SDK call in the middle changes.

LiveThe Claude path - Anthropic SDK5 min▶

The Anthropic messages.create call takes a tools list. You build it straight from what the session discovered - MCP's inputSchema maps directly to Claude's input_schema. When a reply contains a tool_use block, you run the tool and append a tool_result, then call the model again.

client.py · process_query (Claude) async def process_query(self, query: str) -> str: messages = [{"role": "user", "content": query}] tools_resp = await self.session.list_tools() available_tools = [{ "name": tool.name, "description": tool.description, "input_schema": tool.inputSchema, # MCP schema -> Claude tool } for tool in tools_resp.tools] resp = self.anthropic.messages.create( model="claude-sonnet-5", max_tokens=1000, messages=messages, tools=available_tools, ) final_text = [] assistant_content = [] for block in resp.content: if block.type == "text": final_text.append(block.text) assistant_content.append(block) elif block.type == "tool_use": # The model picked the tool and filled the args from the question. result = await self.session.call_tool(block.name, block.input) assistant_content.append(block) messages.append({"role": "assistant", "content": assistant_content}) messages.append({"role": "user", "content": [{ "type": "tool_result", "tool_use_id": block.id, "content": result.content, }]}) follow = self.anthropic.messages.create( model="claude-sonnet-5", max_tokens=1000, messages=messages, tools=available_tools, ) final_text.append(follow.content[0].text) return "\n".join(final_text)

Notice the mapping you will be quizzed on: a model tool_use block becomes one session.call_tool(name, args), and its answer goes back as a tool_result keyed by the same tool_use_id. Same id-pairing discipline as the raw JSON-RPC in b1.

LiveThe Ollama path - local model, no API key5 min▶

The no-API-key path. Swap the Anthropic call for the ollama Python package pointed at a local model such as llama3.2. The MCP half does not change at all - same session, same call_tool. Only the model client and the tool-call field names differ (Ollama returns message.tool_calls, each with function.name and function.arguments).

client_ollama.py · same loop, local model (no API key) import ollama # pip install ollama ; run `ollama pull llama3.2` first async def process_query_ollama(session, query: str) -> str: tools_resp = await session.list_tools() tools = [{ "type": "function", "function": { "name": t.name, "description": t.description, "parameters": t.inputSchema, # same MCP schema, Ollama shape }, } for t in tools_resp.tools] messages = [{"role": "user", "content": query}] reply = ollama.chat(model="llama3.2", messages=messages, tools=tools) for call in reply.message.tool_calls or []: result = await session.call_tool(call.function.name, call.function.arguments) messages.append(reply.message) messages.append({ "role": "tool", "name": call.function.name, "content": result.content[0].text, }) final = ollama.chat(model="llama3.2", messages=messages) return final.message.content
Why teach both The Claude path ships the best tool-use quality; the Ollama path proves MCP is model-agnostic and runs offline with private data. Same discovery, same call_tool, same result handling. If you can read one, you can read the other.
Self-studyMulti-server clients - one session per server3 min read▶

Real hosts connect to several servers at once - Daybreak plus a filesystem server plus GitHub. The rule from b1 holds: one client session per server. You keep a dict of sessions, merge every server's list_tools into one tool list for the model, and route each call_tool to the session that owns that tool name.

sketch · routing across sessions self.sessions = {} # server_name -> ClientSession self.tool_owner = {} # tool_name -> server_name # ...after connecting each server, record which session owns each tool... owner = self.tool_owner[block.name] result = await self.sessions[owner].call_tool(block.name, block.input)

Watch for name collisions: two servers can both expose a tool called search. Hosts usually namespace by server to keep them apart.

When things fail 5 min live

Three different things can go wrong, at three different layers, and the fix for each is different. A protocol error is a JSON-RPC error object - the request was malformed or named a tool that does not exist. A tool failure is a normal result with isError:true - the tool ran but the work failed. A transport drop is neither - the connection died and no message comes back at all. Your client has to handle all three.

LiveThe three failure layers on the wire4 min▶

Step the error scenario: the client calls a tool the server never declared. What comes back is a JSON-RPC error - not a result. Compare it with the successful tools/call in Part 1: result vs error is the whole distinction.

defensive call - all three layers try: result = await self.session.call_tool(name, args) # layer 3 dies here except Exception as e: return f"Transport/protocol failure: {e}" # layers 1 + 3 if getattr(result, "isError", False): # layer 2 return f"Tool ran but failed: {result.content[0].text}" return result.content[0].text

client.py · main entry point (the runnable file) import asyncio, sys async def main(): if len(sys.argv) < 2: print("Usage: python client.py <path_to_server.py>") sys.exit(1) client = DaybreakClient() try: await client.connect(sys.argv[1]) while True: query = input("\nAsk Daybreak: ").strip() if query.lower() == "quit": break print("\n" + await client.process_query(query)) finally: await client.cleanup() if __name__ == "__main__": asyncio.run(main())
Real world

The client is where product happens. Servers are commodity - once Daybreak exposes clean tools, any client can drive it. The differentiated work is in the client: which model, how you handle multi-step tool chains, how you surface errors to the user, whether you require human approval before a consequential tool. That is why teams write clients even when off-the-shelf hosts exist.

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · Who sends the very first message that opens a session?

The client always initiates. session.initialize() sends the initialize request; the server only ever answers. The model is not on the wire at all - it talks to your client, which talks to the server.

2 · A model reply contains a tool_use block. In your client, that maps to...

tool_use → session.call_tool(name, args) → tool_result keyed by the same tool_use_id → model writes the answer. That is the whole loop, and it is identical for Claude and Ollama.

3 · Your call_tool returns a normal result with isError:true. Which layer failed, and should you retry?

isError:true means the tool executed but the work failed - a normal result, not a JSON-RPC error. Retries only help layer 3 (transport drops). Layers 1 and 2 need a corrected request or app-level handling.
