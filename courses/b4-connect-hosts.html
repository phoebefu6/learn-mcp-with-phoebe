Part 1 · covers Claude Code MCP docs, official "Connect to local MCP servers"

Claude Code: .mcp.json and scopes 8 min live

Claude Code configures MCP servers at three scopes, and the scope decides who sees the server and where the config lives. Precedence runs local > project > user: if the same server name is defined at more than one scope, the more specific one wins. Get the scope right and you never fight config again.

LiveScope decision guide4 min▶

The rule is about audience, not difficulty. Ask "who should have this server?" and the scope falls out:

  • Experimenting alone? Use local. Private to you and this project, gone when you clean up. Nothing leaks into a repo.
  • Team repo where everyone needs it? Use project. The .mcp.json is checked into the repo root, so every teammate who clones gets Daybreak with no setup.
  • A tool you want in every project? Use user. Your personal toolbox - a reference filesystem server, say - available everywhere you work.

Here is the project-scope config. It lives at the repo root as .mcp.json and gets committed:

.mcp.json · project scope, checked into the repo root{ "mcpServers": { "daybreak": { "command": "uv", "args": ["run", "python", "server.py"], "env": { "DAYBREAK_DB": "${DAYBREAK_DB:-./daybreak.db}" } } } }
  • command + args - exactly how to launch your stdio server; the host runs it as a subprocess.
  • env supports variable expansion: ${VAR} and ${VAR:-default} pull from the environment, so secrets and paths never get hard-coded into the checked-in file.
LiveVerifying a server landed4 min▶

Two ways to confirm Claude Code actually loaded your server. First, run /mcp in the session - it lists connected servers and their status. Second, look at how the tools are named:

the host renames your tools by servermcp__daybreak__query_sales mcp__daybreak__top_products mcp__daybreak__subscription_status # pattern: mcp__<server-name>__<tool-name>
  • mcp__daybreak__query_sales - the host prefixes every tool with mcp__ and the server name from your config. Seeing this prefix is proof the server connected and its tools are namespaced.
  • The server name comes from the JSON key ("daybreak"), not from FastMCP("daybreak-mcp") - name the key deliberately, because it shows up in every tool name.
  • If /mcp shows the server failed, the command in your config threw - run it by hand in the terminal to see the error, exactly like the Inspector failures in b2.
Same handshake, no model in b2 When Claude Code launches your server it runs the exact initialize handshake you stepped through in b1 - just automatically, with a real model on the other end this time.

Claude Desktop and beyond 7 min live

Claude Desktop uses a single config file, claude_desktop_config.json, with the same mcpServers shape you just wrote - command and args. Edit it, restart Desktop, and your server appears. This is the payoff moment: the identical server.py now runs in a second host, and you changed zero lines of Python.

LiveDesktop config walkthrough4 min▶

Open Desktop's settings, go to Developer, click Edit Config, and add Daybreak. The file lives at:

where the file livesmacOS: ~/Library/Application Support/Claude/claude_desktop_config.json Windows: %APPDATA%\Claude\claude_desktop_config.json
claude_desktop_config.json · add Daybreak{ "mcpServers": { "daybreak": { "command": "uv", "args": [ "run", "--directory", "/Users/you/daybreak-mcp", "python", "server.py" ] } } }
  • Absolute paths. Desktop does not launch from your project folder, so pass --directory with the full path - a relative path is the number-one Desktop failure.
  • Restart to load. Desktop reads this file only at startup. Fully quit and reopen - not just close the window - for the server to appear.
  • Same shape as .mcp.json under the hood: mcpServers, command, args, optional env. Learn it once.

Reference servers 6 min live

You are not the only server in the host. The MCP project ships official reference servers - filesystem, git/github, memory, and more - that you can install alongside Daybreak. A host with several servers is the normal case, and the tool-name prefix is what keeps them straight.

LivePairing your server with reference servers4 min▶

Add a reference server next to Daybreak in the same config. The filesystem server is the classic pairing - now the model can read a file and query your sales in one conversation:

.mcp.json · two servers, one host{ "mcpServers": { "daybreak": { "command": "uv", "args": ["run", "python", "server.py"] }, "filesystem": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/you/reports"] } } }

Reload, and /mcp lists both. The tools are namespaced - mcp__daybreak__query_sales and mcp__filesystem__read_file - so nothing collides. Now watch the handshake that every one of these servers runs when the host starts it:

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · The same server name is defined at local and user scope. Which wins?

Precedence is local > project > user: the most specific scope wins. A local definition overrides both project and user for that server name.

2 · Where does a project-scope .mcp.json live, and what happens to it?

Project scope means .mcp.json sits at the repo root and is committed. Every teammate who clones the repo gets the server with no extra setup - that is the point of the scope.

3 · You edited claude_desktop_config.json but the server does not appear. Most likely fix?

Claude Desktop loads MCP config at launch. After editing the file you must fully quit and reopen the app (not just close the window) for the new server to load. A relative path is the other common culprit.
